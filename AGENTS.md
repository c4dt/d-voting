# AGENTS.md

Guidance for AI coding agents (and humans) working on this repository.

## Project overview

D-Voting is an e-voting platform built on top of the
[Dela](https://github.com/c4dt/dela) blockchain. Ballots are encrypted
client-side with a key-pair generated by a distributed key generation (DKG)
protocol, shuffled with a verifiable shuffling protocol, and only then
decrypted and revealed. It is a research prototype: do not use it for real
forms.

The system has four high-level components:

- **Blockchain node** - a Dela node extended with the D-Voting smart contract,
  a DKG service, a verifiable shuffling service, and an HTTP proxy.
- **Proxy** - HTTP handlers exposing the node's features to external clients
  (see `proxy/`).
- **Web frontend** - React app used by voters and admins (see
  `web/frontend/`).
- **Web backend** - Express.js server handling authentication and
  authorization, relaying signed requests to the node (see `web/backend/`).

A form (the codebase historically used "election"; new code should use
"form", e.g. `FormID`) follows a strict workflow enforced by the smart
contract: create → cast ballots → shuffle → reveal. Keep this workflow
consistent when touching the contract, the services, or the frontends.

## Repository layout

```
cli/dvoting          Node CLI entry point (build target)
contracts/evoting    D-Voting smart contract and its types
services/dkg         Pedersen DKG service
services/shuffle     Neff verifiable shuffling service
proxy                HTTP handlers for the REST API
web/frontend         React frontend (TypeScript)
web/backend          Express backend (TypeScript)
integration          Integration tests (spun up local node network)
internal             Testing helpers, tracing, custom vet checks (mcheck)
metrics              Prometheus metrics
scripts              Local/Docker environment setup and system tests
docs                 Documentation (docsify, served on GitHub Pages)
Dockerfiles          Dockerfiles for the node, backend, and frontend
docker-compose       Docker Compose configuration (PostgreSQL and services)
```

## Environment

- Go >= 1.25 (see `go.mod`; CI uses Go 1.25).
- Node.js: CI lint jobs use Node 16.
- The Dela `crypto` CLI utility is needed to set up a local blockchain (see
  README.md).
- Docker Compose for the PostgreSQL database and the full Docker setup.

## Common commands

Run Go checks from the repository root:

```sh
make check            # lint + vet + all unit tests except integration
make lint             # staticcheck (also runs `go mod tidy`)
make vet              # custom checks, see "Go style rules" below
go test `go list ./... | grep -v /integration`   # all unit tests
make test_integration # integration tests (go test ./integration -timeout 50s)
make build            # build the `dvoting` binary for the local platform
```

Web frontend (`web/frontend/`):

```sh
npm install
npm start             # mocked mode, no backend needed
REACT_APP_NOMOCK=on npm start   # talk to the real backend/node
npm run eslint        # lint (CI runs this)
npm run prettier-check
```

Web backend (`web/backend/`):

```sh
npm install
cp config.env.template config.env   # first time only
npm start
npm run eslint        # lint (CI runs this)
npm run prettier-check
```

Full local environments and focused system tests are described in
`scripts/README.md` (`./scripts/run_docker.sh`, `./scripts/run_local.sh`,
`./scripts/system-tests/`). Copy `.env.example` to `.env` for Docker setups.

## Testing expectations

- Every Go package keeps its tests next to the code (`*_test.go`); the CI
  (`go_test.yml`) runs `make vet` and all unit tests except `/integration` on
  every pull request.
- Integration tests live in `integration/`; they spin up in-memory node
  networks inside the test itself and are run by a dedicated workflow
  (`go_integration_tests.yml`).
- Frontend tests are end-to-end tests written with Playwright
  (`web/frontend/tests/`, config in `web/frontend/playwright.config.ts`);
  they expect a running development environment (`npm start` in the
  frontend) and are not part of the CI workflows.
- If you add a feature or fix a bug, add or update the corresponding tests.

## Go style rules

Besides standard Go conventions (`gofmt`, comments on exported symbols), this
repository enforces custom checks via `make vet`, implemented in
`internal/mcheck`:

- **Comment length**: no comment line may exceed 80 characters (use
  `// @nolint-next-line` to opt out of a specific comment).
- **No `if` with an initialization statement**: write
  `x := f(); if x != nil {` instead of `if x := f(); x != nil {`.
- `make lint` runs `staticcheck ./...` and `go mod tidy`; keep the module
  tidy (the `replace` directives in `go.mod` are intentional, do not remove
  them).

## Web style rules

- Frontend and backend are linted with ESLint and checked with Prettier in
  CI (`web_frontend_lint.yml`, `web_backend_lint.yml`). Run `npm run
  eslint-fix` and `npm run prettier` before committing.

## Configuration, keys and secrets

- Never commit real secrets, private keys, or passwords. `.env.example` and
  `config.env.template` contain placeholder values only; local copies
  (`.env`, `config.env`) are git-ignored.
- Flags such as `REACT_APP_DEV_LOGIN` and `REACT_APP_SCIPER_ADMIN` are
  debugging helpers and must stay disabled in production configurations.

## Git and pull request conventions

- Keep commits atomic and descriptive.
- Open pull requests using the template in
  `.github/pull_request_template.md`, assign yourself, and link the related
  issue with a closing keyword (e.g. `Closes #123`).
- Update `CHANGELOG.md` (Keep a Changelog format) for user-visible changes.
- Documentation lives in `docs/` (docsify); update it when behavior or APIs
  change.
